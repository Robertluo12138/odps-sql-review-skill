# 指标口径解释规则手册（metric_rules）

> 本文用于指导 AI Agent 如何在评审报告的 **第 5 节 “指标口径解释”**
> 中描述每一个聚合指标。
>
> 评审 SQL 的关键不是 “它能不能跑”，而是 “它算出来的数到底是什么”。
> 没有口径解释的指标就是不可上线的指标。

---

## 一、必须解释的指标类型

只要 SELECT 列表里出现下面任一类，就必须给出口径解释：

- `SUM(...)`
- `COUNT(...)`
- `COUNT(DISTINCT ...)`
- `AVG(...)`
- `MIN(...)`、`MAX(...)`
- `approx_distinct(...)` / `approx_count_distinct(...)`
- 比率类表达式 `<aggA> / <aggB>`
- `CASE WHEN ... THEN ... END` 包裹的条件聚合
- `SUM(IF(cond, 1, 0))` 这类等价的条件聚合

普通维度列（如 `user_id`、`shop_id`、`dt`）不算指标，不需要在第 5 节
里解释，但应在 GROUP BY 粒度里被提及。

---

## 二、每个指标必须填写的字段

报告中第 5 节，每个指标都要给出：

| 字段 | 说明 | 不确定时怎么写 |
|---|---|---|
| 指标名称 | SELECT 中的 alias，没 alias 时用表达式 | 直接写表达式 |
| 分子 | 计算的对象 / SUM 的列 / COUNT 的列 / 分子表达式 | `需要确认` |
| 分母 | 比率指标的分母；非比率指标可写 “非比率指标，无分母” | `需要确认` |
| 过滤条件 | CASE WHEN 内的过滤 + WHERE 中作用于该指标的条件 | `需要确认` |
| GROUP BY 粒度 | 实际聚合粒度（外层 GROUP BY 列） | `需要确认` |
| 是否存在重复计算风险 | JOIN 是否可能放大行数？多表 JOIN 后 SUM 是否安全？ | `需要确认` |
| 是否需要业务确认 | 业务定义是否和 SQL 一致？ | 默认 `是` |

---

## 三、按指标类型的解释规范

### 1. SUM(col)
- **分子**：被 SUM 的列；
- **分母**：无（写 “非比率指标，无分母”）；
- **重复计算风险**：若 JOIN 后右表非唯一 → 是；
- **关键问题**：col 是否在 JOIN 后被重复计入。

### 2. COUNT(1) / COUNT(*)
- **分子**：分组内的行数；
- **重复计算风险**：JOIN 行数膨胀直接放大该值；
- **业务问题**：到底统计的是什么对象（订单？支付？请求？）。

### 3. COUNT(DISTINCT col)
- **分子**：col 的不重复值个数；
- **业务问题**：col 在该 SQL 上下文里能否唯一标识对象；
- **性能问题**：长周期 + 大基数 → 高风险，必须建议中间表或近似值；
- **重复计算风险**：JOIN 行数膨胀通常 **不影响** distinct 结果，
  但会影响 `SUM` / `COUNT(1)`，要分开评估。

### 4. AVG(col)
- **分子**：`SUM(col)`；
- **分母**：`COUNT(col)`（注意 NULL 会被忽略）；
- **业务问题**：是否需要按业务粒度先去重再求平均；
- **风险**：分母 = 0 时返回 NULL，不会报错。

### 5. MIN / MAX
- 单个聚合，本身不会引起重复计算；
- 业务问题：是否带过滤；NULL 处理是否符合预期。

### 6. 比率指标 `aggA / aggB`
- **分子**：aggA；
- **分母**：aggB；
- **过滤条件**：分子和分母是否同粒度、同口径；
- **风险**：分母 = 0 → 返回 NULL，建议改写为
  `aggA / nullif(aggB, 0)`；
- **业务问题**：分子是不是分母的子集？比率应该 ≤ 1 还是可以 > 1？

### 7. CASE WHEN 条件聚合
- **过滤条件**：把每个 WHEN 子句作为内嵌过滤列出；
- **业务问题**：每个 WHEN 的业务定义是否与文档一致；
- **风险**：WHEN 顺序错误 / 边界值漏掉某个分类。

### 8. approx_distinct / approx_count_distinct
- **业务问题**：业务是否接受近似值（误差通常 ~2%）；
- **绝对禁止**：财务、计费、合规等强精确场景；
- **建议写法**：必须在指标命名中体现 “_approx” 或在文档中标注。

## 四、长周期 / 用户级指标（重点）

如果指标 alias 中含有 `mau` / `yau` / `wau` / `dau` / `active_user`
/ `uv` 等关键字，且 SQL 在原始明细表上用 `COUNT DISTINCT user_id`，
必须在第 5 节里加备注：

> 该指标是长周期去重指标。当前 SQL 直接对原始明细表做
> `COUNT DISTINCT user_id`，性能与正确性均有风险。
> 建议落地按天聚合的 `dws_xxx_user_active_di`（dt + user_id 粒度），
> 在该中间表上计算月活 / 年活；如业务允许近似值可使用
> `approx_distinct`，不允许时禁止把日 UV 累加为 MAU。

---

## 五、什么时候标记 “需要业务确认”

默认所有指标都写 `是`，因为：

- 同一个 “GMV” 在不同业务线可能含税 / 不含税；
- 同一个 “订单数” 可能按 order_id 也可能按主单号；
- 同一个 “用户数” 可能按设备、按账号、按手机号；
- 同一个 “活跃” 可能定义为登录、点击、停留 ≥ N 秒、付费等；
- 同一个 “退款金额” 可能含运费 / 不含运费 / 含优惠券。

只有在用户已经在 prompt 中显式给出业务定义，且 SQL 写法与该定义
完全一致时，才允许写 `否`。

## 六、报告示例

```markdown
#### 指标：`pay_user_cnt`
- 表达式：`COUNT(DISTINCT CASE WHEN action = 'pay' THEN user_id END)`
- 聚合类型：COUNT_DISTINCT
- 分子：`CASE WHEN action = 'pay' THEN user_id END` 去重后的用户数
- 分母：非比率指标，无分母
- 过滤条件：`action = 'pay'`（来自 CASE WHEN）；外层 WHERE：`dt BETWEEN '20240101' AND '20241231'`
- GROUP BY 粒度：全局聚合（无 GROUP BY，单值）
- 是否存在重复计算风险：是 —— 建议在原始明细表上先按 (dt, user_id) 去重，再统计
- 是否需要业务确认：是 —— 是否仅统计 `action = 'pay'` 还是包含 `repay` / `partial_pay` / `refund` 等行为
- 备注：长周期去重指标，建议落地 `dws_xxx_user_active_di` 后再计算
```
